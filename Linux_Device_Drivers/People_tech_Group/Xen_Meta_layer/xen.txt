Xen_Meta_Layer












Run Xen Hypervisor on Raspberry Pi 5 using Yocto by adding the meta-virtualization layer and enabling Xen support.

Prerequisites

Host: Ubuntu 20.04 / 22.04 (recommended)

Yocto release: kirkstone or newer (mandatory for RPi5)

Working Yocto build for Raspberry Pi 5

Internet access

Basic Yocto knowledge (bitbake, layers, conf files)

Step 1: Set Up Yocto for Raspberry Pi 5

Clone Yocto (example: kirkstone):

mkdir yocto-rpi5 && cd yocto-rpi5

git clone -b kirkstone https://git.yoctoproject.org/poky
git clone -b kirkstone https://git.yoctoproject.org/meta-raspberrypi


Initialize build:

source poky/oe-init-build-env build


Add Raspberry Pi layer:

bitbake-layers add-layer ../meta-raspberrypi


Set machine in conf/local.conf:

MACHINE = "raspberrypi5"

Step 2: Add Xen Meta Layer (meta-virtualization)

Clone the virtualization layer:

cd ..
git clone -b kirkstone https://git.yoctoproject.org/meta-virtualization


Add it to Yocto:

cd build
bitbake-layers add-layer ../meta-virtualization


Verify:

bitbake-layers show-layers


You should see:

meta-virtualization
meta-raspberrypi
poky

Step 3: Enable Xen in Yocto Configuration

Edit conf/local.conf:

DISTRO_FEATURES:append = " virtualization xen"


Enable Xen tools:

IMAGE_INSTALL:append = " xen xen-tools"


(Optional but recommended):

VIRTUAL-RUNTIME_init_manager = "systemd"
DISTRO_FEATURES:append = " systemd"

Step 4: Enable Xen in Kernel Configuration

Raspberry Pi kernel must support Xen.

Create kernel config fragment:

mkdir -p meta-custom/recipes-kernel/linux/files


xen.cfg:

CONFIG_XEN=y
CONFIG_XEN_DOM0=y
CONFIG_XEN_PVH=y
CONFIG_XEN_GRANT_DEV_ALLOC=y
CONFIG_XEN_GNTDEV=y
CONFIG_XEN_EVTCHN=y


Append in kernel recipe (.bbappend):

FILESEXTRAPATHS:prepend := "${THISDIR}/files:"
SRC_URI += "file://xen.cfg"

Step 5: Enable Xen Boot Support

Edit conf/local.conf:

RPI_USE_U_BOOT = "1"
ENABLE_UART = "1"


Xen requires U-Boot for proper boot sequencing.

Step 6: Build Xen-Enabled Image

Use a full image:

bitbake core-image-full-cmdline


or:

bitbake core-image-minimal


Build time: 1–3 hours (first build).

Step 7: Flash Image to SD Card
sudo dd if=core-image-full-cmdline-raspberrypi5.wic \
        of=/dev/sdX bs=4M status=progress
sync

Step 8: Boot & Verify Xen

On serial console or HDMI:

xl info


Expected output:

host                   : dom0
xen_version            : 4.x
nr_cpus                : 4


Check hypervisor:

dmesg | grep Xen

Common Blockers & Fixes
Problem	Fix
Xen not starting	Ensure RPI_USE_U_BOOT=1
Kernel panic	Check Xen kernel configs
xl missing	Ensure xen-tools installed
Dom0 fails	Verify memory settings

Memory tweak (optional):

XEN_DOM0_MEM = "512M"

1️⃣ What is Dom0 and DomU?

When Xen boots, it creates special domains (virtual machines).

🔹 Dom0 (Domain 0)

First VM started by Xen

Has special privileges

Controls hardware access

Creates and manages other VMs

Think of Dom0 as:

The manager Linux that controls the hypervisor.

It:

Has device drivers

Talks to hardware

Uses xl tool to create other VMs

Handles networking & storage for guests

🔹 DomU (Domain User)

Normal guest VM

Created by Dom0

Limited privileges

Cannot access hardware directly (unless assigned)

It can be:

Linux

RT Linux

RTOS

Minimal embedded OS

CPU core pinning

Core 0 → Dom0 (Linux control)

Visual View
4
2️⃣ Is It “One Core = One OS”?

Not necessarily.

There are two modes:

🔹 Mode A: Dedicated Core (Real-Time Friendly)

You pin:

DomU RTOS → Core 1 only


That VM runs only on Core 1.

No other VM touches that core.

✔ Predictable
✔ Low jitter
✔ Real-time safe

This is common in automotive.

🔹 Mode B: Shared Core (General Purpose)

Multiple VMs share cores.

Example:

Core 2,3 shared between AI and networking VM


Xen scheduler switches between them.

This is like normal virtualization.

3️⃣ Can AI Run on One Core and RTOS on Another?

Yes — absolutely.

Example:

Core 0 → Xen + Dom0
Core 1 → Motor Control RTOS
Core 2,3 → AI Linux


Now:

AI spikes CPU → only affects Core 2,3

RTOS on Core 1 → unaffected

This is why hypervisors are powerful in embedded systems.

4️⃣ Important Clarification

Even if you assign:

DomU → Core 1


That VM still has:

Its own virtual memory

Virtual devices

Virtual interrupts

Xen manages hardware underneath.

So it’s not physically splitting the chip —
it’s logically partitioning resources.

5️⃣ What Happens Internally?

When you assign a core:

Xen scheduler restricts VM to specific pCPU

Interrupt routing is adjusted

Memory region is reserved

Cache isolation may apply

The VM thinks:

“I own this CPU”

But Xen still controls it.

It’s not mandatory one OS per core.
You choose how to partition.
