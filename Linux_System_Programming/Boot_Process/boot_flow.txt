🖥️ Complete Linux Boot Process





1. Complete boot flow diagram


1. Power ON
Power supply starts the hardware

2. BIOS / UEFI firmware
CPU initialization, RAM and hardware setup

3. POST and hardware checks
Checks essential hardware; firmware setup follows

4. Select boot device
SSD / HDD / USB / network, according to boot order

5. Bootloader
UEFI: EFI application such as GRUB
Legacy BIOS: boot code in MBR, then GRUB stages

6. Linux kernel loads
Kernel image + boot parameters + initramfs

7. Kernel initialization
CPU, memory, scheduler, drivers, interrupts

8. Initramfs / initrd
Temporary root filesystem; finds and mounts the real root

9. Switch to real root filesystem
Mounts the installed Linux system, often on the SSD

10. PID 1 — systemd
Starts services and targets according to dependencies

11. Login screen / Desktop
Display manager, user session, desktop environment








2. Step-by-step explanation


Step 1: Power ON ⚡

When you press the laptop's power button:
- The power circuitry supplies power to the motherboard.
- The CPU starts executing instructions from a predefined firmware entry point.
- The firmware stored in motherboard flash memory begins executing.
At this point, Linux has not started yet.



Step 2: BIOS / UEFI firmware
BIOS and UEFI are firmware interfaces responsible for initializing the computer and starting a bootloader.
Legacy BIOS	Modern UEFI
Older firmware interface	Modern firmware interface
Commonly boots through MBR boot code	Commonly loads an EFI executable
Traditionally uses 16-bit real-mode boot code initially	Uses its own firmware execution environment
Often paired with MBR partitioning	Commonly paired with GPT partitioning
Limited traditional boot process	Supports features such as Secure Boot
A 64-bit laptop can use either Legacy BIOS or UEFI. 64-bit architecture does not automatically mean UEFI.




Step 3: POST — Power-On Self-Test 🔍
POST is the firmware's initial hardware-checking process.
It checks or initializes essential components, such as:
- CPU
- RAM
- Graphics/display hardware
- Keyboard and other basic devices
- Storage devices and other platform components
If a critical component fails, the laptop may show an error, beep, or stop booting.
POST is part of firmware startup, not a separate Linux program.





Step 4: Select a bootable device 💽
The firmware determines which device or boot entry to try according to its boot order.
Examples:
- Internal SSD or HDD
- Bootable USB drive
- Network boot
- Other firmware-supported devices
On a UEFI laptop, the firmware typically reads boot entries stored in NVRAM and locates a bootloader file on the EFI System Partition (ESP).
On a Legacy BIOS system, the firmware typically selects a disk and reads its initial boot sector.
A device being bootable means it contains the necessary boot information and files for the selected boot method.





Step 5: First-stage and second-stage bootloader
This part is different for Legacy BIOS and UEFI.
A. Legacy BIOS boot path
BIOS firmware


MBR — Master Boot Record
First sector of a traditionally partitioned boot disk


GRUB initial boot code
Loads further bootloader code


GRUB core and modules
Finds the GRUB configuration, kernel and initramfs


B. Modern UEFI boot path
UEFI firmware


EFI System Partition (ESP)
Usually a FAT-formatted partition


EFI bootloader — e.g., GRUB
A file such as \EFI\ubuntu\grubx64.efi on typical x86-64 Ubuntu installations


GRUB configuration and modules
Locates the Linux kernel and initramfs


What is MBR?
MBR stands for Master Boot Record. In the traditional layout, it is the first 512-byte sector of the disk and contains:
- Boot code
- The partition table (four primary partition entries in the standard layout)
- A boot signature
The MBR boot code is very small, so it normally loads additional bootloader code rather than loading the complete Linux kernel itself.
Note: MBR is associated with the traditional Legacy BIOS boot path. UEFI boot from a GPT disk normally uses an EFI executable from the ESP, not the MBR boot code. A GPT disk can still contain a protective MBR.
What is GRUB?
GRUB stands for GRand Unified Bootloader. It lets you select an operating system or kernel and passes the required boot parameters to Linux.
Important GRUB components and files:
- grubx64.efi — a typical x86-64 UEFI GRUB executable.
- GRUB modules — provide filesystem, disk, and other support.
- /boot/grub/grub.cfg — generated GRUB menu configuration on typical Ubuntu systems.
- /etc/default/grub — settings used to generate the configuration.
- /etc/grub.d/ — scripts used to generate menu entries.
On Ubuntu, update-grub regenerates grub.cfg from the configuration settings and detected boot entries. Do not normally edit the generated grub.cfg directly.





3. Step 6: Linux kernel loading 🐧
After selecting the Linux entry, GRUB loads the kernel image and the initramfs into memory.
Typical Ubuntu files include:
File	Purpose
/boot/vmlinuz-<version>	Compressed Linux kernel image
/boot/initrd.img-<version>	Initramfs image
/boot/config-<version>	Kernel build configuration
/boot/System.map-<version>	Kernel symbol-address map, useful for debugging
The exact files depend on the distribution and kernel installation.
What happens with a 64-bit kernel?
On a typical x86-64 laptop:
1. The bootloader prepares the kernel boot information and required memory objects.
2. The kernel's entry code establishes the execution environment it needs.
3. The kernel initializes 64-bit CPU facilities, memory management, and other core subsystems.
4. Kernel initialization continues until it can start its initial userspace process.
A 64-bit kernel can address memory using 64-bit architecture facilities, subject to CPU, kernel, and platform limitations. It does not mean every pointer or physical address uses all 64 bits.
What are boot parameters?
Boot parameters are arguments passed by the bootloader to the kernel.
For example:
root=UUID=<root-filesystem-uuid> ro quiet splash


- root= identifies the root filesystem to use.
- ro requests an initial read-only root mount in the usual Linux boot flow.
- quiet reduces routine kernel messages.
- splash requests splash-screen behavior when supported.
The exact parameters vary by installation.





4. Step 7: Kernel initialization
The Linux kernel begins initializing the operating system's core facilities.
Typical work includes:
1. CPU and architecture initialization.
2. Physical memory detection and memory management.
3. Virtual memory and page tables.
4. Scheduler initialization.
5. Interrupt handling and timers.
6. Built-in driver initialization.
7. Kernel subsystem setup, such as filesystems and networking.
8. Preparing to start the first userspace process.
What about device drivers?
Drivers can be built into the kernel or loaded as separate kernel modules.
- Built-in drivers: available as part of the kernel image.
- Loadable modules: separate .ko files that can be loaded when needed.
Examples include storage, USB, network, graphics, and filesystem drivers. Some critical drivers must be available early enough to access the real root filesystem.
Common module-related paths:
/lib/modules/<kernel-version>/


Useful commands after boot:
uname -r
lsmod
dmesg


uname -r shows the running kernel version, lsmod lists loaded modules, and dmesg displays kernel messages.






5. Step 8: initramfs / initrd
This is one of the most important stages for understanding Linux booting.
initramfs means initial RAM filesystem. It is a temporary, small userspace environment loaded into RAM by the bootloader alongside the kernel.
Why is it needed?
Imagine Ubuntu is installed on an SSD, but the kernel needs a storage driver, filesystem driver, or encryption support before it can access the installed system. Those components may not be built into the kernel.
The initramfs provides the tools and modules needed to prepare the real root filesystem.
Kernel starts

Mount initramfs as temporary root
Available in RAM

Run early userspace scripts
Load needed modules, detect storage, unlock encrypted volumes if configured

Locate and mount the real root filesystem
Usually the installed Linux root filesystem on the SSD

Switch to the real root
Continue normal userspace startup


What is inside initramfs?
It commonly contains:
- Early userspace utilities and scripts.
- Essential kernel modules.
- Storage and filesystem support.
- Device discovery tools.
- Configuration for finding the real root filesystem.
- Optional LVM, RAID, or disk-encryption support.
On Ubuntu, inspect the initramfs-related files and tools with:
ls -lh /boot/initrd.img-*
lsinitramfs /boot/initrd.img-$(uname -r) | head -40


The generated initramfs commonly contains an early /init program. This is not the same as the final /sbin/init on the installed root filesystem.
Is initramfs the same as init?
No.
initramfs	init
Temporary early userspace environment	Initial userspace process of the normal system
Helps prepare the real root filesystem	Starts and manages normal system startup
Runs before the normal root transition	Usually runs after the transition to the real root
Often has an early /init script/program	On Ubuntu, normally systemd as PID 1
The word initrd is also commonly used in file names and boot terminology. Modern Linux distributions generally use an initramfs archive, even if the image is named initrd.img.






6. Step 9: Mount the real root filesystem
Once the kernel can access the installed system, early userspace locates and mounts the root filesystem.
For example, a simplified Linux filesystem layout might look like this:
/
├── bin
├── boot
├── dev
├── etc
├── home
├── lib
├── proc
├── root
├── run
├── sbin
├── sys
├── tmp
├── usr
└── var


The root directory / is the top of the Linux filesystem hierarchy.
Important directories:
Directory	Purpose
/boot	Kernel and boot-related files
/etc	System configuration files
/dev	Device nodes
/proc	Virtual filesystem exposing process and kernel information
/sys	Kernel device and subsystem information
/lib/modules	Loadable kernel modules, commonly on merged-/usr systems as a link into /usr/lib/modules
/usr	Most user-space programs, libraries and supporting files
/var	Logs, caches and other variable data
/home	Users' home directories
How does Linux identify the root partition?
The boot configuration can use a device path, UUID, PARTUUID, or other supported mechanism. A UUID is useful because device names such as /dev/sda2 can change.
Check your mounted filesystems:
findmnt /
lsblk -f
cat /etc/fstab


/etc/fstab describes filesystems to mount and their options. The boot process may use the root UUID in the kernel command line, while fstab helps configure the root and other filesystems during startup.






7. Step 10: init and systemd
After the system switches to the real root, Linux starts its initial userspace process. On a typical Ubuntu installation, this is systemd, running as PID 1.
You can verify it with:
ps -p 1 -o pid,comm,args


Typical output:
PID  COMMAND  COMMAND
1    systemd  /sbin/init


The displayed command may differ slightly by distribution.
What is systemd?
systemd is the system and service manager. It coordinates system startup, starts services, manages dependencies, and brings the system to a selected target.
It may start or coordinate:
- Device management through udev-related components.
- Filesystem mounts.
- Swap configuration.
- Networking services.
- Logging services.
- Background daemons.
- Login services.
- The graphical display manager.
These jobs can run concurrently when their dependencies permit it; they do not all need to execute in one fixed linear sequence.
Systemd startup flow
systemd — PID 1

Units and dependency relationships
Services, mounts, sockets, devices, targets and more

System services
Logging, networking, background jobs


System preparation
Mounts, devices, prerequisites



Selected systemd target
Often graphical.target for a desktop, or multi-user.target for a text-based system

Login screen or text login


What is a systemd target?
A target groups units into a desired system state.
Target	Purpose
basic.target	Basic system initialization
multi-user.target	Multi-user system with services, usually text-mode login
graphical.target	Graphical login and desktop-related startup
rescue.target	Rescue environment
emergency.target	Minimal emergency environment
The default target is commonly graphical.target on a desktop Ubuntu installation. Targets are not simply a rigid list of steps: they pull in dependencies, and some work happens in parallel.
Useful commands:
systemctl get-default
systemctl list-units --type=service
systemctl --failed
systemd-analyze time
systemd-analyze blame
systemd-analyze critical-chain


systemd-analyze blame reports time spent activating units, but a long time does not necessarily mean a unit delayed the overall boot; some units start in parallel.






8. Step 11: Configuration files and dependencies ⚙️
This is the part you specifically asked about: which configuration files control booting, and how dependencies work.
A. Important boot configuration files

1. /etc/fstab
Filesystem mount configuration
Specifies filesystems, mount points, filesystem types and options. It can configure the root filesystem and other partitions, although the root is usually mounted initially by the early boot process.


2. /etc/default/grub
GRUB settings on typical Ubuntu installations
Controls settings such as the default boot entry, timeout and kernel command-line options. After changing it, regenerate the GRUB configuration with sudo update-grub.


3. /boot/grub/grub.cfg
Generated GRUB menu configuration
Contains boot menu entries, kernel paths, initramfs paths and boot parameters. It is usually generated from /etc/default/grub, scripts in /etc/grub.d/, and related configuration.


4. /etc/initramfs-tools/
Initramfs generation configuration on Ubuntu
Contains configuration and scripts used to build the initramfs. The generated image is normally stored as /boot/initrd.img-<version>.


5. /etc/systemd/
System and service-manager configuration
Contains systemd configuration and unit-related settings. Other units may be installed under /usr/lib/systemd/system/ or /lib/systemd/system/, depending on the distribution's layout.


6. /etc/modules-load.d/ and /etc/modprobe.d/
Kernel module configuration
The first can specify modules to load at boot; the second can configure module options, aliases and blacklists. Many drivers are instead loaded automatically when needed.

B. How do dependencies work?
Suppose a service needs networking before it can start. systemd uses unit relationships to manage the order and requirements.
For example:
network.target
      ↓
network-dependent service
      ↓
application starts


This is a simplified illustration, not a guarantee that network.target means a usable internet connection. A service that requires configured network connectivity may need network-online.target and the appropriate network wait service.
Common dependency directives include:
Directive	Meaning
Wants=	Pulls in another unit as a desired dependency
Requires=	Pulls in a required unit; failure can affect the dependent unit
After=	Specifies startup ordering
Before=	Specifies that another unit should start later
WantedBy=	Specifies the target that can pull in a unit when enabled
Important: After= alone does not start the other unit. It only controls ordering if both units are being started.
For example, a service file might look like this:
[Unit]
Description=My Application
After=network.target

[Service]
ExecStart=/usr/local/bin/myapp
Restart=on-failure

[Install]
WantedBy=multi-user.target


This is a basic example. Save it as /etc/systemd/system/myapp.service if you want to create a real service, and make sure /usr/local/bin/myapp exists and is executable.
To enable it:
sudo systemctl daemon-reload
sudo systemctl enable --now myapp.service
systemctl status myapp.service


- daemon-reload reloads systemd's unit definitions.
- enable configures the service to start automatically through its installation dependencies.
- --now starts it immediately as well.






9. Step 12: Login screen and desktop 🖥️
Once systemd has started the required services, the graphical login process can begin.
A typical Ubuntu desktop flow is:
systemd
   ↓
graphical.target
   ↓
Display manager (e.g., GDM)
   ↓
Login screen
   ↓
User authentication
   ↓
Desktop session (e.g., GNOME)
   ↓
Applications and desktop services


The display manager presents the graphical login screen. After successful authentication, it launches the user's desktop session.
For a terminal-only system, Linux may instead provide a text login through a getty service.
At this point, the laptop is ready for normal use.






10. Complete flow at a glance
Here is the full sequence to remember for interviews and Linux System Programming:
1. Power ON — electrical power reaches the hardware.
2. BIOS/UEFI — firmware starts executing.
3. POST — firmware checks and initializes essential hardware.
4. Boot device selection — SSD, USB or another supported boot source is selected.
5. Bootloader — Legacy BIOS commonly uses MBR boot code; UEFI normally launches an EFI bootloader such as GRUB.
6. GRUB — loads the kernel, initramfs and boot parameters.
7. Linux kernel — initializes the CPU, memory, scheduler, interrupts and core subsystems.
8. initramfs — prepares storage and finds the real root filesystem.
9. Root filesystem — the installed Linux system becomes the active root.
10. systemd (PID 1) — starts units according to dependencies and ordering.
11. Targets and services — networking, logging, mounts and other services become available.
12. Login and desktop — the display manager or text login is presented.



11. Commands to investigate your laptop's actual boot process
Since you're learning Linux, try these commands on your Ubuntu system. They help connect the theory to what is really happening.
| Command | What it shows |
|---|---|
| uname -m | CPU architecture seen by the running kernel, e.g. x86_64 |
| uname -r | Running kernel version |
| test -d /sys/firmware/efi && echo UEFI || echo Legacy | Whether the current Linux boot used UEFI |
| lsblk -f | Disks, partitions, filesystems and UUIDs |
| findmnt / | Root filesystem mount details |
| cat /proc/cmdline | Kernel boot parameters |
| ps -p 1 -o pid,comm,args | Initial userspace process |
| systemctl get-default | Default systemd target |
| journalctl -b -k | Kernel messages from the current boot |
| journalctl -b | System logs from the current boot |
| systemd-analyze time | Approximate firmware, bootloader and kernel/userspace timing when available |
Run the commands individually in your terminal.




12. What if booting fails?
Different failures point to different stages:
Symptom	Possible stage or cause
Laptop does not power on	Power circuitry or hardware
POST error or firmware screen	Hardware initialization or firmware
“No bootable device”	Boot order, storage, boot entry or bootloader
GRUB rescue prompt	GRUB configuration, modules or filesystem access
Kernel panic	Kernel, drivers, root filesystem or another critical failure
Unable to mount root fs	Incorrect root parameter or missing storage/filesystem support
Emergency mode	Filesystem mount failure, fstab issue or another critical startup problem
Login screen never appears	Failed services, display manager or graphics driver



Final one-line definition

The Linux boot process is the sequence in which firmware initializes the laptop, the bootloader loads the Linux kernel and initramfs, the kernel prepares the real root filesystem, and systemd starts the services required to reach the login screen or desktop. 🚀
