1. What is Valgrind? 🤔
Valgrind is a programming tool used to detect memory errors and analyze memory usage in programs.
It is especially useful when developing C and C++ applications on Linux.
For example, in C you might:
- Allocate memory using malloc().
- Forget to release it using free().
- Access an array outside its boundaries.
- Use memory that has not been initialized.
- Access memory after freeing it.
These errors can cause crashes, incorrect results, or memory leaks. Valgrind can help identify many of them.




2. Why do we use Valgrind? 🎯
Problem	What Valgrind can help detect
Memory leak	Allocated memory that is never freed
Invalid read	Reading memory outside a valid region
Invalid write	Writing outside allocated memory
Use after free	Accessing memory after it has been freed
Uninitialized value	Using values that were never properly initialized
Heap misuse	Incorrect use of dynamically allocated memory
Example: Suppose your program allocates 100 bytes using malloc() but never calls free(). Valgrind can report that some allocated memory is still reachable or lost when the program exits.
One important distinction: Valgrind is not a compiler. GCC compiles your code; Valgrind runs the compiled program under its analysis tools.




3. Step 1 — Install Valgrind on Ubuntu 🛠️
Open your terminal and run:
sudo apt update
sudo apt install valgrind


Check whether it is installed:
valgrind --version


Example output:
valgrind-3.22.0


The version may be different on your system.




4. Step 2 — Create a C program with a memory leak
Let's intentionally create a memory leak so you can see how Valgrind detects it.
Create a file:
nano memory_leak.c


Write this code:

#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int *ptr = malloc(5 * sizeof(int));

    if (ptr == NULL)
    {
        perror("malloc");
        return 1;
    }

    ptr[0] = 10;
    ptr[1] = 20;

    printf("First value: %d\n", ptr[0]);
    printf("Second value: %d\n", ptr[1]);

    /* Intentionally not calling free(ptr) */

    return 0;
}



Save the file in Nano:
- Press Ctrl + O
- Press Enter
- Press Ctrl + X
What is the problem here?
int *ptr = malloc(5 * sizeof(int));


This dynamically allocates memory for five integers.
But we never call:
free(ptr);


The allocated memory is not explicitly released by our program before it exits. This is the memory leak we want Valgrind to investigate.




5. Step 3 — Compile the program with debugging information
Run:
gcc -g -Wall memory_leak.c -o memory_leak


What do the options mean?
Option	Purpose
-g	Includes debugging information, helping Valgrind identify source-code lines
-Wall	Enables many useful compiler warnings
-o memory_leak	Names the executable memory_leak
The -g option is especially useful because it helps you locate the source of an error.




6. Step 4 — Run the program normally
First, execute the program without Valgrind:
./memory_leak


Output:
First value: 10
Second value: 20


The program appears to work correctly. However, it contains a memory-management problem.
This is why memory bugs are difficult to find: a program can produce the correct output and still have errors.




7. Step 5 — Run Valgrind on the program 🔍
Now run:
valgrind --leak-check=full ./memory_leak


Valgrind executes your program and reports memory-related problems.
To get more detailed leak information, use:
valgrind --leak-check=full --show-leak-kinds=all ./memory_leak


You may see output similar to this:
==1234== HEAP SUMMARY:
==1234==     in use at exit: 20 bytes in 1 blocks
==1234==   total heap usage: 1 allocs, 0 frees, 20 bytes allocated

==1234== 20 bytes in 1 blocks are definitely lost
==1234==    at ... malloc ...
==1234==    by ... main (memory_leak.c:6)

==1234== LEAK SUMMARY:
==1234==    definitely lost: 20 bytes in 1 blocks


The process ID, line numbers, and exact output formatting will vary. The leak details above illustrate the expected result.
How to understand the output
Message	Meaning
20 bytes	Five integers × four bytes each on a typical system
1 allocs	One allocation was made
0 frees	No explicit heap deallocation was recorded
definitely lost	Valgrind cannot find a pointer to this allocated block at program exit
memory_leak.c:6	The source location associated with the allocation
The exact byte count depends on the size of int on your platform.
What does definitely lost mean?
It means the program has lost all pointers that could be used to reach the allocated memory. The program can no longer explicitly free that block.
Other leak classifications include:
- Indirectly lost: Memory reachable only through another lost allocation.
- Possibly lost: Valgrind cannot establish that the allocation is fully reachable because of how its pointers are stored.
- Still reachable: A pointer to the memory remains accessible when the program exits. This is not automatically a leak that needs fixing.




8. Step 6 — Fix the memory leak ✅
Edit the program:
nano memory_leak.c


Add free(ptr); after using the allocated memory.

#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int *ptr = malloc(5 * sizeof(int));

    if (ptr == NULL)
    {
        perror("malloc");
        return 1;
    }

    ptr[0] = 10;
    ptr[1] = 20;

    printf("First value: %d\n", ptr[0]);
    printf("Second value: %d\n", ptr[1]);

    free(ptr);
    ptr = NULL;

    return 0;
}



Now compile and run Valgrind again:
gcc -g -Wall memory_leak.c -o memory_leak
valgrind --leak-check=full --show-leak-kinds=all ./memory_leak


You should now see a heap summary similar to:
HEAP SUMMARY:
    in use at exit: 0 bytes in 0 blocks
  total heap usage: 1 allocs, 1 frees

All heap blocks were freed -- no leaks are possible


🎉 You have now detected a memory leak, fixed it, and verified the result using Valgrind!





9. Step 7 — Detect invalid memory access
Valgrind also helps detect invalid reads and writes.
Create another file:
nano invalid_access.c


Example:

#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int *ptr = malloc(3 * sizeof(int));

    if (ptr == NULL)
        return 1;

    ptr[0] = 10;
    ptr[1] = 20;
    ptr[2] = 30;

    /* Invalid: valid indexes are 0, 1, and 2 */
    ptr[3] = 40;

    free(ptr);

    return 0;
}



Compile and run:
gcc -g -Wall invalid_access.c -o invalid_access
valgrind ./invalid_access


Valgrind should report an Invalid write because the program tries to write beyond the allocated array.
This is a common C programming bug: allocating space for three integers does not give you permission to access index 3.





10. Useful Valgrind commands 📝
Command	Purpose
valgrind ./program	Run basic memory checks
valgrind --leak-check=full ./program	Detailed leak checking
valgrind --show-leak-kinds=all ./program	Show all leak categories
valgrind --track-origins=yes ./program	Help trace the origin of uninitialized values
valgrind --log-file=valgrind.log ./program	Save output to a log file
valgrind --leak-check=full --error-exitcode=1 ./program	Return a nonzero exit status when Valgrind detects errors
For debugging uninitialized values, combine the options:
valgrind --track-origins=yes --leak-check=full ./program






11. Valgrind vs GCC vs GDB
Tool	Main purpose
GCC	Compiles C/C++ programs
GDB	Debugs execution, variables, breakpoints and crashes
Valgrind	Detects memory errors and analyzes memory usage
For your Linux System Programming and device-driver learning, Valgrind is particularly useful for testing user-space C programs involving malloc(), pointers, linked lists, file processing and sockets.
Note that Valgrind is not a general replacement for kernel debugging tools. It does not normally run Linux kernel code itself under Memcheck.
🎯 Your practical workflow
1. Write your C program
For example, a program using pointers or malloc().



2. Compile with -g
gcc -g program.c -o program



3. Run Valgrind
valgrind --leak-check=full ./program



4. Fix reported errors
Check the source line, correct the bug, and run Valgrind again.



One-line definition: Valgrind is a dynamic analysis tool that runs programs to help detect memory leaks, invalid memory accesses, and other memory-related errors.
